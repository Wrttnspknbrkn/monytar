## P0 — Security / Data Integrity

| # | Area | Issue | Root Cause | Status | Notes |
|---|---|---|---|---|---|
| P0-1 | Auth/RBAC | Any authenticated user could PATCH their own `users` row via the Supabase REST API directly and set `role: 'admin'` | `002_rls_policies.sql`'s "Users can update own profile" policy had `USING (id = auth.uid())` with no `WITH CHECK` restricting which columns change | **Verified fixed** | Migration `017_security_hardening.sql`: BEFORE UPDATE trigger freezes `role`/`organization_id`/`is_active` on self-updates unless actor is already admin or the write comes from service-role. Live-tested: escalation attempt silently reverted, legitimate self-edit still works. |
| P0-2 | Approvals | Manager/finance/admin could approve or reject their own submitted request | `/approve` and `/reject` had org+department scoping but no `employee_id != actor` check | **Verified fixed** | `.neq("employee_id", userId)` added to both routes; live-tested via forged session against the real API route (403 "not authorized"). |
| P0-3 | API | Generic `PATCH /api/requests/[id]` accepted an unvalidated body and let any admin/finance/manager write `status: 'approved'`/`'paid'` directly, bypassing the whole approval workflow, department scoping, and notifications | No zod validation, no field allowlist, relied entirely on a broad RLS UPDATE policy | **Verified fixed** | Route confirmed unused by the frontend (dead but live/exploitable). Hardened with a strict field allowlist (`expenseRequestSchema.partial()`, status/approval fields excluded). DELETE also fixed to report 404 honestly instead of a fake `success:true` on 0 rows affected. |
| P0-4 | RLS | `notifications` and `budget_alerts` tables had RLS enabled with no INSERT policy at all | Migration oversight | **Verified fixed** | Both features were silently non-functional (every insert failed RLS, caught and swallowed). Added scoped INSERT policies in `017_security_hardening.sql`. |
| P0-5 | RLS | `check_subscription_feature()` (unused today) is `SECURITY DEFINER` with no pinned `search_path`, callable by `anon` | Migration `003_subscription_columns.sql` predates the search_path convention adopted later | **Verified fixed** | Re-declared with `SET search_path = public, pg_temp` in `017_security_hardening.sql`. |
| P0-6 | Cross-tenant data | `GET /api/demo-leads` (platform-wide marketing leads, no `organization_id` column) was gated only by `role === 'admin'` — meaning **any customer's org-admin could read every other customer's leads** once the underlying "always empty" bug was fixed | Comment in the migration assumed a service-role client would be used for reads; the route actually used the RLS client, which had no SELECT policy at all — so it accidentally failed safe (always empty) until fixed naively | **Verified fixed** | Now requires the caller's email to be in a `PLATFORM_ADMIN_EMAILS` env allowlist AND reads via the admin/service-role client. Fails closed if the env var is unset. **Needs external config**: `PLATFORM_ADMIN_EMAILS` must be set for anyone to see this page at all. |
| P0-7 | RBAC/tenant isolation | Full live cross-tenant test across all major tables (departments, vendors, expense_requests, users, org_settings, notifications, budget_alerts) and full route-by-route server-side authorization inventory | — | **Verified (agent)** | Live-tested: full cross-tenant isolation holds on every table (reads and writes both blocked), no role-escalation/IDOR found on `users`/`expense_requests` write paths beyond what 017 already fixed. All test data cleaned up. |
| P0-10 | Billing | Any org admin could self-upgrade their subscription tier/status/seat-limit for free via a direct REST PATCH, **and** set an arbitrary `stripe_customer_id` to open another real Stripe customer's live billing portal through their own org's Settings page | `"Admins can update organization"` policy (`005_billing_rls_policies.sql`) has `USING` but no `WITH CHECK` and no column restriction — same class of bug as P0-1, on a different table, found by live-testing | **Fixed (unverified — needs migration run)** | Live-verified exploit: `PATCH /rest/v1/organizations` as an org admin successfully set `subscription_tier:"enterprise"`, `max_users:999999`, and an injected `stripe_customer_id`. Fixed via a `BEFORE UPDATE` trigger (migration `019`) freezing every billing/subscription column unless the write is service-role (Stripe webhook/signup route) — same proven pattern as the `users` table fix. |
| P0-11 | Financial workflow | **The real UI never calls the hardened approve/reject/mark-paid/create-request API routes at all** — it wrote directly to Supabase via raw functions in `lib/hooks/use-supabase-data.ts` with none of those routes' business rules (no self-approval guard, no status/department scoping, no auto-approve computation, no notifications). This made every earlier "fix" to those API routes ineffective in production, since nothing called them | The app's established pattern uses direct-Supabase calls from React hooks for most CRUD; approve/reject/mark-paid/create-request happened to also have separate, unused API routes that were never wired up | **Fixed (unverified — needs migration run + manual smoke test)** | Rewired `lib/providers/data-provider.tsx`'s approve/reject/mark-paid/create handlers to call the real API routes via `fetch()`; deleted the dangerous raw functions from `use-supabase-data.ts` entirely so they can't be reintroduced. Also hardened the RLS policy itself as defense-in-depth (migration `018`): the privileged-role branch of the `expense_requests` UPDATE policy now excludes `employee_id = auth.uid()` (no self-approval regardless of code path) and enforces manager department scoping at the DB level, not just in route code. |
| P0-12 | Data integrity | `finance_notes` (the "Additional Notes" field on the New Request form) was never added as a real column — any user who filled it in got a hard database error on submit (`PGRST204`) | Column never migrated despite being in `lib/types.ts` and the form since inception | **Fixed (unverified — needs migration run)** | Live-verified the failure via direct insert. Added via migration `020`. Also discovered and fixed while here: `expenseRequestSchema` validated for legacy `title`/`description` fields the real form never sends (it sends `purpose`, superseding them per migration `012`) — rewrote the schema to match reality, which is what let request creation finally route through real server-side validation at all. |
| P0-8 | Currency | `getCurrencyMeta()` in `lib/currency/index.ts` only recognizes 8 currency codes (USD, EUR, GBP, CAD, AUD, JPY, INR, NGN), but the Settings page's currency picker offers 16 (also CHF, GHS, KES, ZAR, BRL, MXN, SGD, AED) — selecting any of the other 8 silently formats as USD everywhere, with no error | Two independent, unsynced currency lists (`app/(dashboard)/settings/page.tsx`'s local `SUPPORTED_CURRENCIES` vs `lib/currency/index.ts`'s) | Open | Not a security issue but a silent-wrong-financial-data issue — elevated to P0-adjacent because it means displayed amounts can be *wrong* (mislabeled currency), not just US-defaulted. |
| P0-9 | Signup | If the `/api/auth/signup` fetch throws for ANY reason (network blip, timeout, CORS) against a fully configured production backend, the catch block shows `toast.success("Account created! (Demo Mode)")` and advances the wizard as if the account exists | `app/signup/page.tsx:115-120` — the network-error fallback was written for genuine demo-mode (no Supabase configured) but fires on any thrown error, not just that specific signal | Open | A user who hits a transient network error during signup is told they have an account, then can't log in later with no explanation — a fabricated success state on the most important conversion flow in the app. |

| # | Area | Issue | Root Cause | Status | Notes |

| P1-1 | Currency | Dashboard, Reports, Approvals list, Requests list, command-search, and the request-card component all display amounts hardcoded to USD regardless of the organization's configured currency | Of ~29 `formatCurrency()` call sites app-wide, only Settings, the Departments page, and the single-request detail page passed a `currency` argument — every other call site used the function's `currency = "USD"` default | **Fixed** | **The flagship bug from the spec.** Fixed at the root: added `currencyCode`/`formatAmount(amount)` to the shared `useData()` context (`lib/providers/data-provider.tsx`), derived once from `orgSettings.default_currency`, and switched every identified call site (dashboard, reports incl. all 3 chart tick formatters, approvals, requests list, command-search, request-card, the New Request form's amount input/label) to use it — so a call site can no longer "forget" the currency argument.
